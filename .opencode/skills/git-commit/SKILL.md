# Git Commit

## When to use me

Use this skill whenever the user asks to commit changes, stage files, or draft
a commit message. Also use it when the user asks "закоммить" / "сделай коммит".

## Hard rules for this repository

1. **Never commit before the user has reviewed the changes.** If review has not
   happened yet, show `git status` and `git diff` first and wait for
   confirmation.
2. **Never `git push`.** Only push when the user explicitly says so.
3. **Never `git add -A` blindly.** Stage only the files that belong to the
   change; list them by name.
4. Never amend, rebase, force-push, or use `git commit -i` unless asked.
5. Never touch git config.

## Procedure

1. Inspect state:
   - `git status` — what changed, what is untracked;
   - `git diff` — unstaged changes;
   - `git diff --staged` — already staged;
   - `git log --oneline -10` — recent message style in this repo.
2. Show the user a concise summary of the diff and ask for review.
3. After approval, stage only the intended files:
   - `git add <path> <path>`
4. Verify again with `git diff --staged`.
5. Commit.

## Commit message rules

- Imperative mood, lowercase first word, no trailing period:
  `add task file for login check`
- Subject line up to ~72 characters.
- Body (only when the change is non-obvious): wrap at 72 characters, explain
  _why_, not _what_.
- No emoji, no `WIP`, no ticket references unless the user asks.
- One logical change per commit; if the diff mixes unrelated things, split it
  or ask the user.

## Examples

Good:

```
add login check task and solution
```

Good with body:

```
rename exercise files to kebab-case

Follows the international file naming rules agreed in AGENTS.md.
```

Bad:

```
Fixed stuff
```

```
feat: ✨ login task (auto-generated by agent)
```

## If something fails

- If a commit hook rejects the commit, fix the reported problem and commit
  again — do not amend the failed commit, do not skip hooks.
- If the working tree is dirty with unrelated files, do not stage them; ask
  the user what to do.
